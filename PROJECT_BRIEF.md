# Project Brief

> How to use this template: replace the bracketed prompts under each heading
> with your own content, then delete these blockquote instructions. Writing
> **Unknown** is a valid, useful answer — it shows what to investigate next.
> Keep it short. Mark sections that do not apply instead of leaving them
> blank.

## Part A — The Brief

### 1. One-paragraph summary

[What is this project, in 2–4 sentences? What does it change, and for whom?
If you can't write this yet, write your best attempt and mark it "rough".]

### 2. The problem

[What is wrong, missing, or slow today? Who feels it, and how often?
Avoid solutions here — describe the situation, not the fix.]

### 3. Goals and non-goals

- Goal: [What must be true when this is done? 1–3 items.]
- Non-goals: [What is explicitly *out* of bounds for this project?
  Listing non-goals helps prevent scope creep (the project quietly
  growing) later.]

### 4. Success criteria

[How will you know it worked? Prefer things you can check:
"I can complete X in under Y minutes", "Z no longer happens".
If you can't measure it yet, write what you *would* measure and mark it Unknown.]

### 5. Who it's for

[Who are the users or audience? What do they know, expect, and need?
If it's just you, say so — that's a valid answer.]

### 6. Scope

- In: [What this first version includes.]
- Out: [What it deliberately does not include, even if tempting.]

### 7. Constraints

[Fixed limits you must work within: time, budget, skills, tools, rules,
deadlines, things you're not allowed to change. Write "None known" if so.]

> Sections 8–11 are optional extras. Keep the ones that apply to this
> project and delete the rest — but say so rather than leaving them blank.

### 8. Data and integrations

[What data does the project handle — where does it come from, what form
is it in, where does it go? What outside systems, services, or tools
must it talk to, if any? "None" is a valid answer.]

### 9. Privacy and security

[What must be protected — personal data, credentials, files, anything
sensitive? Who is allowed to see or change it? If nothing sensitive is
involved, say that here so it's a decision, not an oversight.]

### 10. Accessibility

[Who needs to be able to use this, on what devices, connections, or
setups? Any specific needs or standards to meet? If accessibility work
is out of scope for this version, record that here.]

### 11. Delivery constraints

[Where must this run or ship — which platform, device, or environment;
online or offline; any limits on cost, size, or setup effort? What must
be true for someone to receive it and start using it?]

### 12. Assumptions

[Things you're treating as true for now but haven't verified.
Each one is a small risk — that's fine, we just want them visible.]

### 13. Open questions

| # | Question | How we might answer it | Status |
| - | -------- | ---------------------- | ------ |
| 1 | [ … ]    | [ ask someone / try it / research ] | Open |

### 14. Risks

[What could delay or prevent this project? One line each.
Mark each: likely / possible / unlikely.]

### 15. Decisions made

[Short log of choices already locked in, and why. One line each.
New decisions go here as the project runs.]

## Part B — Implementation Plan

> Fill this in *after* Part A is mostly solid. Plans are guesses with
> structure — expect to revise, and mark steps that depend on an
> unresolved open question.

### 1. Approach

[In a few sentences: how will you build this? Big pieces first, or a
thin end-to-end version first (a minimal cut that works start to
finish)? What order, and why?]

### 2. Milestones

| # | Milestone        | Done when…              | Depends on | Status |
| - | ---------------- | ----------------------- | ---------- | ------ |
| 1 | [ e.g. skeleton ] | [ observable outcome ]  | —          | Not started |

### 3. Acceptance checks

[The short list of checks that must pass before this counts as done —
the success criteria in Part A made concrete. Write each one so someone
else could run it without you: do X, expect Y. These are what the build
is tested against and what a final audit runs.]

### 4. Next actions

[The 1–3 smallest useful things to do next. Each should be concrete
enough to start today and small enough to finish soon.]

- [ ] [Action — how you'll know it's done]

### 5. Deferred work

[Ideas postponed for a later version. Note when to revisit each one.]

### 6. Review checkpoint

[When will you re-read this brief and plan — after a milestone, a week,
a month? What would make you change course?]
